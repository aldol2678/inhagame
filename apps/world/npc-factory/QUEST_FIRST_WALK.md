# First campus walk · local candidate

The quest is a Social S3 / Quest Q0–Q2 candidate. It does not change Social S1 completion or the frozen INKYUNG-20 Population NPC source. Nana-yul (001) and Ga-yudam (002) receive separate runtime placement and quest dialogue; the original candidate still forbids generated NPC quest capability.

Route: talk to Nana-yul at the main gate → visit the main hall entrance → visit the Inkyung pond → hear Ga-yudam's request at the photo point → return to Nana-yul at the gate. Each stage is account scoped and ordered. The tracked objective replaces the existing first-tour HUD only while this quest is active. Quest actions use authored lines and no Gemini calls. Existing signed-in interest dialogue still uses the AI pilot and its quota. Completion runs one server reward (Progression P1c): `reward.quest.first_campus`, the `badge.main_gate` badge plus +100 campus EXP. It has no currency or relationship reward.

The first-walk quest migration (private `20260926070000_world_quest_first_walk_v1`, now part of the public baseline `20261001213132_public_baseline.sql`) adds private progress and a service-role-only RPC. The browser sends only an event; Cloud Run verifies the permanent account and calls the RPC. Out-of-order and duplicate events do not advance progress. The original AI Cloud Run service gains `/quest`; Vercel exposes it only when `NPC_QUEST_ENABLED=1` and `NPC_AI_CLOUD_RUN_URL` is configured. The migration must be present in the target database before the route is enabled. The localhost server uses an in-memory account-scoped store that resets when the process stops.

Visit events are based on the browser's place zone and proximity to existing world landmarks. They are client-originated soft evidence: the server does not independently prove physical movement. What the server does enforce is ordered, authenticated, account-scoped progress (each event only advances from the stage before it) and a one-time reward. The P1c reward migration (private `20260929073413_world_quest_first_campus_reward_p1c`, also in the public baseline) runs the reward inside `advance_world_quest_v1`, only on the call that itself moves the row from stage 4 to 5, in the same transaction, with the stable idempotency key `grant:quest.first_campus:<user uuid>`. A failed reward rolls the stage back so the final talk can be retried; replays, status calls and repeated `talk_001` return no reward. The browser sends only the event and never calls a Reward RPC.

This is acceptable only because the reward is a one-time, low-value onboarding reward with no currency. Do not reuse this pattern for high-value or repeatable rewards: those need authoritative evidence (for example a server-judged action, as in the MCM landlord run) and their own review.
